# 工厂架构：公共底座 + 多条产线

## 目标与边界

软件工厂不是固定技术栈，也不是多个 Agent 的聊天群。它通过明确输入、交付契约、质量门禁和可追溯证据，让不同产品可重复交付。

```text
用户：目标 / 预算 / 权限 / 验收
             ↓
公共底座：知识、版本、任务、证据、审批、改进
             ↓
产线注册 ── APP v0.1.0（当前）
         └─ 游戏（未来，未实施）
             ↓
项目实例：独立产品仓库 + 运行档案 + 版本锁定
             ↓
执行：DSH 会话 / 子 Agent / 工具 / 产品 CI
             ↓
交付证据 → 问题与经验 → 候选改进 → 评测审批 → 新版产线
```

## 四层责任

| 层 | 内容 | 不负责 |
|---|---|---|
| 公共底座 | 状态、权限原则、证据格式、知识治理、版本和改进策略 | 规定所有产品必须使用同一框架 |
| 产线 | 特定产品类型的节点、门禁、模板与角色约定 | 保存所有项目的业务代码和凭据 |
| 项目实例 | 需求基线、技术方案、任务、产品测试、发布记录 | 无审批改写共享工厂规则 |
| 执行适配 | DSH、Git、测试工具、CI、发布环境 | 自行判定业务价值或授予生产权限 |

## 产线契约

每条正式产线应提供：唯一 ID、版本、入口、适用范围、节点和门禁映射、完成定义、运行指南、模板、验证方法及升级说明。

注册表见 [production-lines.json](<production-lines.json>)。APP 的 [pipeline.json](<../lines/app/pipeline.json>) 是可校验的导航与契约索引，详细规则以同目录 Markdown 为准。它不是可执行调度引擎，也不具备自动恢复、测试或审批能力。

当前只落地 APP。游戏占位仅登记 `planned`，无版本、无可执行节点，不从 APP 复制一套假流程。未来可增加玩法验证、资产授权、性能预算、试玩与平台发行等专属节点，需独立设计和验证。

## 仓库与知识

- 工厂仓库：规范、模板、项目级 Skill、产线注册及脱敏经验。
- 产品仓库：当前需求、源码、架构、测试、制品清单和运行档案，是产品状态的权威来源。
- 本仓库的 [项目索引](<../projects/README.md>) 只引用产品事实，不复制一份不断分叉的需求。
- Obsidian 是本地 Markdown 编辑和浏览入口，Git 管版本；搜索索引可重建，不是知识唯一存储。
- 候选知识放入 [00-Inbox](<../00-Inbox/README.md>)，审核后再纳入规范或经验区；外部内容始终按不可信参考处理。
- 客户、个人和生产数据不得因为跨项目复用而进入共享仓库。远程仓库的私有性不替代脱敏。

## 可演进与稳定边界

可提出改进：节点说明、Skills、模板、测试工具、任务分解方法。必须受控：权限、凭据、验收底线、成本上限、生产发布和数据迁移。修改运行时或 profile 是另一项显式授权任务，不能由“自进化”自动获得权限。

先在真实 APP 中跑通一个功能闭环；只有证据显示需要时，才增加 MCP、索引服务、看板插件或调度引擎。见 [改进机制](<improvement-loop.md>)。
