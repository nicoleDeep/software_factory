# 公共运行规范

## 角色与责任

| 角色 | 责任 | 不能自行决定 |
|---|---|---|
| 用户 / 产品负责人 | 目标、范围、预算、验收与风险接受 | 不把缺证据视为通过 |
| 协调者 | 节点状态、依赖、拆分、证据归档 | 放宽要求以宣布完成 |
| 实现者 | 代码、测试、配置与文档 | 自己的报告代替独立审查 |
| 审查 / 测试者 | 独立检查需求符合性、风险、实际测试 | 修改验收口径来掩盖失败 |
| 发布执行者 | 在批准的版本、环境和范围内操作 | 自行批准生产发布或破坏性迁移 |
| 知识维护者 | 脱敏、去重、来源核验和候选归档 | 将一例成功泛化为全局规则 |

个人可以兼任多个角色，但要保留不同检查视角和批准记录。Agent 的角色提示不是安全隔离；开发、测试和生产凭据必须实际隔离。

## 状态与转移

任务：`proposed → ready → in_progress → in_review → done`。

- 只有 DoR 满足才能 `ready`；DoD 和所需批准满足才能 `done`。
- 依赖或信息缺失记为 `blocked`，记录阻塞事实、负责人和下一步；恢复后回到适当节点。此状态是任务记录，不替代 DSH Goal 的生命周期规则。
- 审查不通过回到 `in_progress`，保留问题和失败证据；不得静默改成完成。
- `cancelled` 需记录决定者、原因及残留变更处置。

门禁状态统一为：`pending`（待评审）、`blocked`（缺输入/授权/证据）、`rejected`（标准未满足）、`passed`（全部适用条件满足）、`conditional`（仅有获批限时接受的 P2）、`waived`（整个门禁被证明确实不适用）。`waived` 必须具名批准并记录适用范围和理由，不能绕过实际适用门禁；单个不适用检查项不必把整道门禁标为 waived。`conditional` 必须有风险影响、补救措施、责任人和到期时间；不可豁免项见 [APP 质量门禁](<../lines/app/quality-gates.md>)。

## 证据最小集合

每次验证至少记录：需求/任务 ID、产品提交 SHA、工厂提交 SHA及产线版本、命令或人工步骤、执行环境、时间、退出码/结论、报告位置、已知限制。发布制品另外记录摘要和构建来源。

- “未执行”“无法验证”“失败”和“通过”必须区分。
- 更改代码、依赖、测试、配置或制品后，重新验证受影响范围；不得把旧结果直接绑定到新版本。
- 在 [门禁模板](<../templates/gate-review.md>) 记录批准人及原始批准依据，不伪造签字。
- 初期关键门禁由用户批准，CI 和 Agent 提供证据；本仓库没有实现自动审批系统。

## 并行、恢复与预算

- 并行任务先确认接口与写入边界；独立 worktree 优于多人/多 Agent 写同一目录。
- 协调者审阅最终 diff 并在合并状态运行相关测试。格式化器、生成器也算写入者。
- 恢复任务先读取运行档案、当前 Git 状态与已有证据，不重复已完成步骤，不盲目重放支付、发布或迁移。
- 项目启动时填写时间/成本预算、最大重试次数和升级联系人。超出预算须请求决定；本规范不宣称已在 DSH 中配置硬限额。
- 分支、提交、版本标签、产品发布和生产部署是不同操作，不因为获准编写代码而自动全部获得授权。

## 裁剪

原型、内部工具、正式产品可以裁剪文档厚度和测试矩阵；先在项目档案记录理由、风险、批准者。不允许用“个人项目”跳过密钥保护、数据安全、核心功能验收和真实验证。
