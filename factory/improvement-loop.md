# 用真实 APP 驱动产线改进

## 两个循环分开

产品循环：需求 → 实现 → 验证 → 验收 → 发布。

工厂循环：观察 → 问题提案 → 改进假设 → 隔离评测 → 批准 → 版本发布 → 观察与回滚。

产品问题先在产品仓库修复，不为了修复产品而悄悄修改共享流水线。执行者可生成候选经验，但只有获批的变更才成为正式规则。

## 提案状态

`observed → triaged → proposed → evaluating → approved → released → monitored`。

其他结果：`rejected`（无收益/不适用）、`deferred`（缺证据/不优先）、`rolled_back`（上线后退化）。每次状态变化记录日期、责任人和依据，不把 Agent 自评当用户批准。

## 操作步骤

1. **记录事实**：复制 [改进模板](<../templates/improvement.md>) 到 `improvements/IMP-编号-主题.md`。引用项目、任务、工厂版本、失败现象、脱敏证据和影响。
2. **判断根因**：区分产品 bug、知识缺失、流程缺陷、工具故障和模型执行偏差。不把所有问题都转成新规则。
3. **提出最小变更**：描述原规则、新规则、适用范围、不适用情形、影响节点、风险、预算及回滚方案。
4. **隔离实现**：独立分支/worktree；更新受影响文档、模板、Skill、结构索引和测试。保留旧基线，不直接覆盖在途任务的运行快照。
5. **对比评测**：固定代码、环境、输入和验收口径，比较旧版/候选版；用原始失败案例加独立回归案例，避免只对单一案例过拟合。模型任务重复运行并记录次数和波动。
6. **评审与批准**：查看是否解决问题、是否引入退化、是否增加人工时间和成本。涉及验收、安全、权限、发布的变更必须人工批准；初版不自动晋级任何工厂规则。
7. **发布版本**：在一个提交中同步产线 VERSION、注册表、pipeline.json、Skill 相关引用与 CHANGELOG；记录批准和验证报告。可在明确授权下创建版本标签，不覆盖旧标签。
8. **项目迁移**：新项目采用新版本；在途项目在检查点选择升级/不升级，记录旧新 SHA、影响范围、补测结果和批准。
9. **观察与回滚**：出现退化时先停止新项目采用候选版本，通过新提交恢复旧规则，不重写共享历史；同步模板/Skill/索引。产品代码是否需要回滚另行评估，不能与工厂版本混为一谈。

## 评测指标

| 维度 | 记录内容 |
|---|---|
| 正确性 | 验收通过率、漏检、回归缺陷 |
| 交付效率 | 总耗时、人工介入时间、返工次数 |
| 成本 | 模型用量/费用、服务费用；缺失记未知，不杜撰 |
| 知识质量 | 检索适用性、过期知识误用、证据完整性 |
| 安全 | 越权、敏感信息泄漏、无授权发布 |

阈值在评测前写入提案，不能看完结果再降低标准。评测用例及判定规则由独立审查者/用户维护，不能通过删除失败用例获得通过。低风险可以用轻量人工对照，高风险必须有针对性验证。

## 版本约定

- `PATCH`：澄清、链接、模板修复，不改变既有放行义务。
- `MINOR`：新增可选能力或兼容扩展，需说明采用方法。
- `MAJOR`：改变必需准入/准出、状态语义或不兼容契约。
- v0.x 仍按上述风险分类写清兼容性，不能以“未稳定”为由静默改变行为。
- APP 和未来游戏分别版本化；公共规范变更要检查所有正式产线。项目始终记录工厂提交 SHA，单看版本号不足以复现。

## 什么应该成为知识

单次问题先形成 [候选经验](<../templates/lesson.md>)。有来源、适用边界和验证证据后才标记 `verified`；失效条目标记 `deprecated` 并指向替代项。不要自动把全量聊天、客户资料和密钥上传到 Git。

当前 v0.1.0 的主要待验证假设：10 节点/5 门禁是否足够轻量、任务模板是否帮助恢复、证据字段是否足够、开发过程中的改进提案是否能减少后续返工。首个 APP 要验证这些假设，而不是默认它们已经成立。
