# 首个项目试运行验证清单（v0.1 基线）

目的：第一个真实 APP 跑产线时，用它把 v0.1 基线的“待验证假设”变成有数据的结论，供[改进闭环](<improvement-loop.md>)裁决。这是测量工具，不是门禁；填写它不等于产品通过验收。

## 使用方法

- 项目启动时复制本表的假设表到项目运行档案第 10 节（或独立文件），每个里程碑后更新。
- 每行记录：实际值 / 发生次数 / 结论（假设成立 | 需修改（附提案 ID） | 证据不足（附缺口））。
- 项目结束（G5）时把结论转成改进提案或经验条目；不要中途为“让表好看”修改口径。

## 待验证假设

| ID | 假设 | 怎么测 | 记录位置 |
|---|---|---|---|
| H1 轻量性 | 10 节点/5 门禁不会淹没个人开发者 | 每个门禁的人工介入次数与耗时；每周花在流程文档上的时间 | 运行档案 §7 |
| H2 可恢复 | 任务包足以在中断后恢复 | 每次中断恢复：恢复耗时、是否重复已完成步骤 | 运行档案 §6 |
| H3 证据充分 | 任务包字段能直接支撑门禁判断 | 每次门禁评审：缺哪个字段、临时补了什么 | 门禁记录 |
| H4 改进有效 | 提案能减少同类返工 | 提案数、被采纳数、同类问题复发次数 | improvements/ |
| H5 Skill 可发现 | 新会话能发现 `app-production-line` | 见下方现场验证步骤 | 本文件 |
| H6 知识流转 | 候选经验被后续任务检索使用 | 候选条目数、被引用次数、误用过期知识次数 | 00-Inbox/ |

## H5 现场验证步骤

1. 在 DSH 新建会话，工作目录选择本仓库（Vault 根目录）。
2. 查看会话可用技能，确认出现 `app-production-line`。
3. 若未出现：按 DSH 文档核对项目根发现（最近 `.git` 祖先）与 `.dsh/skills` 扫描规则，把现象记为改进提案证据。

现场验证已通过（2026-11-23）：DSH 会话把工作目录切换到本仓库根目录后，可用技能目录即时刷新，`app-production-line` 出现在列表中，且正文加载成功（内容为 v0.1.1 版本）。结论：H5 在“工作目录位于 Vault 根目录”场景成立，无需重启会话。产品仓库场景已做机械验证（2026-11-23，测试产品仓库实测）：项目根切换后本 Skill 按预期不再出现在技能目录（印证需显式引用）；产品仓库 `AGENTS.md` 指令链正常注入；按绝对路径读取本 Skill 正文成功；切回本仓库后技能恢复出现在目录。首个项目待实测的仅剩工作流层面（引用配置是否顺手、版本锁定是否被遵守），技术可行性已确认。

## 成本与效率基线

| 指标 | 记录方法 |
|---|---|
| 首个端到端切片总耗时 | 从 G1 通过到 G4 通过 |
| 模型用量/费用 | 按 DSH 会话统计；缺失记“未知”，不估算 |
| 人工介入总时长 | 各门禁与抽查时间之和 |
| 返工次数 | 任务从 in_review 打回 in_progress 的次数 |
| 阻塞时长 | 节点处于 blocked 的时间与原因 |

结论一律区分：成立 / 需修改（附提案 ID）/ 证据不足（附缺口）。首个项目结束后本清单的裁决结果决定 v0.2 的方向。
