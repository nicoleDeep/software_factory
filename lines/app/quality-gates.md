# APP 质量门禁 v0.1.1

> 与[APP 流程](<pipeline.md>)配套。这里规定判断方法，不包含真实项目的测试结果、批准记录或发布许可。未执行写“未验证”，未批准写“待批准”。

## 1. 通用决策规则

门禁针对“明确范围 + 明确版本 + 明确证据”作决定，而不是对项目永久盖章。功能切片可重复经过门禁；已有结论仅在范围、风险和证据基线仍有效时复用。

统一状态：

| 状态 | 判定与后续动作 |
| --- | --- |
| pending（待评审） | 输入齐备但尚未收到所需批准，不得越门禁推进受控动作。 |
| blocked（阻塞） | 输入、责任人、环境、授权或证据缺失；登记补齐人、时间和恢复条件，不猜测通过。 |
| rejected（不通过） | 证据已显示不满足标准；记录原因并返回对应节点修复。 |
| passed（通过） | 适用标准全部满足，所需责任人已实际批准，结论可追溯。 |
| conditional（有条件通过） | 仅存在允许接受的 P2，且批准、补偿措施、责任人与到期日齐全；不是用来绕过未执行的必需测试。 |
| waived（不适用） | 整道门禁确实不适用，记录具体范围、理由及人工批准；证据缺失不是不适用，不可豁免风险不得借此放行。 |

- 判定使用[门禁评审记录](<../../templates/gate-review.md>)：门禁编号、切片/版本、标准、证据、未满足项、结论、实际批准人、时间、返回节点和复评触发条件。空白字段不等于批准。
- 所需批准人缺席或授权不明时阻塞；人工作出价值判断、风险接受、业务验收及生产发布授权。AI 只能辅助整理，不冒签、不推断沉默同意。
- 性能、兼容性、业务目标与观察窗口在项目内预先约定，最迟在 G2 固定，并在对应测试/观测开始前留存版本。不得测试后调低阈值、缩小设备范围或缩短窗口以把失败改为通过。
- 需求发生真实变化时，先记录变更理由与影响，由相应责任人重新批准标准、重开受影响门禁并重新验证；保留旧标准和失败证据。不能以变更名义掩盖质量退化。
- 不设置跨项目统一的代码覆盖率百分比。测试充分性以验收项、关键业务路径、异常状态、风险和变更影响的证据映射判断；覆盖率仅可作辅助信号。
- 不适用项必须记录理由与批准，且不能把安全、数据保护、业务验收或必要验证整体标为不适用。证据不可获得不是“不适用”。

## 2. 共享 DoR：可以承诺实现的准备条件

以下为 APP-05/06 的共同准入标准；探索性调研或隔离原型可先做，但不冒充正式实现就绪。

- [ ] 目标用户、问题、功能切片及纳入/排除范围明确，有实际需求责任人。
- [ ] 验收标准可观察、可执行，覆盖主路径和关键异常路径；业务规则无关键歧义。
- [ ] 相关交互、接口、数据契约足以实现；未知事项已分配验证人和时限，阻断未知已消除。
- [ ] 依赖、权限、环境、测试数据和设备可以获得；凭据走受控配置，不写入文档或源码。
- [ ] 风险分级、测试方法、性能/兼容约束及证据保全方式已约定；相应 G1/G2 结论有效。
- [ ] 任务大小可审查，有实现者、审查者、验收者及失败返回路径；责任角色已映射到实际授权主体。

任一必需项不满足即阻塞正式实现；允许把“补齐该项”本身拆成独立探索任务。

## 3. 共享 DoD：可以声称完成的最低条件

DoD 随产物类型适用：文档节点提供可审阅决定与输入证据，代码节点补齐实现/测试证据，发布节点还须满足 G3/G4 和交付核验；不能以“文档已写”替代运行验证。

- [ ] 约定产物齐备，验收项与证据逐项关联；未执行、失败、不适用分别明示。
- [ ] 适用审查和验证已完成，记录真实结果、执行环境、时间、命令/步骤及退出码（工具有退出码时）；不把计划步骤写成执行事实。
- [ ] 无未解决 P0/P1，无不可豁免风险；P2 按下节具有有效接受记录。
- [ ] 代码/配置/接口/用户说明及运行交接资料随变更更新，敏感信息已排除。
- [ ] 责任人与批准结论真实可追溯；版本、任务、制品及证据关系可复核。
- [ ] 遗留事项有责任人、截止日、验证方式与复评触发条件；需重开的门禁已识别。

任务 DoD 不等于发布 DoD；一次单元测试通过不等于 G3，一次业务演示成功不等于 G4。

## 4. 缺陷、风险与例外

| 级别 | 判定示例 | 处理要求 |
| --- | --- | --- |
| P0 | 严重安全事件/漏洞、核心服务大面积失效、不可恢复的数据丢失或破坏等灾难性影响。 | 阻断门禁及发布；运行中立即启动止损和事件处置。 |
| P1 | 核心业务流程不可用、重大结果错误、广泛崩溃，或承诺支持的关键平台无法完成主要任务。 | 阻断门禁及发布；修复并提供复测证据后重评。 |
| P2 | 非核心、影响有限且可控的缺陷，有合理绕行或补偿，不损害关键验收、安全与数据完整性。 | 默认修复；仅可经授权批准限时接受。 |

- 按实际影响分级，不凭修复难度或上线时间降级；有争议由质量负责人召集业务、技术及相关安全/数据负责人裁定，裁定前按较高风险处理。
- **严重安全风险与不可恢复数据风险不得豁免**，不论被贴成何种优先级。P0/P1 不得以业务着急、灰度、免责声明或“有条件通过”绕过。
- P2 接受记录必须包含：问题及影响范围、分级理由、剩余风险、补偿/绕行措施、修复任务、责任人、明确到期日、复测方式、失效触发条件、实际批准人和时间。
- P2 由业务负责人接受影响，技术负责人及质量负责人确认分级与补偿可行；涉及安全/数据时相关负责人共同确认。发布负责人在 G4 核对接受仍有效。
- 到期、影响扩大、补偿失效或基线变化时接受自动失效；阻断后续相关门禁/发布，运行负责人评估是否暂停灰度、关闭功能或执行恢复预案。延期必须重新评审，不能自动续期。

## 5. 五道门禁

### G1 — 价值与范围（APP-02 后）

**判断问题**：为什么做、为谁做、这次到底交付什么，能否客观验收？

- **输入/证据**：立项决定、问题与用户证据、范围/排除项、优先级、业务规则、验收例子、约束与责任人；使用[项目运行记录](<../../templates/project-run.md>)承载。
- **通过条件**：价值假设有可测信号；本次切片边界和验收口径无关键歧义；业务负责人和资源边界明确；影响设计的约束已列出并指定补齐时点。无法确认核心业务规则即阻塞。
- **负责 / 批准**：产品负责人准备；业务负责人批准价值与范围，技术/质量负责人确认可行性待验证项及可测性。
- **失败返回**：价值假设不成立回 APP-01；范围/标准不清回 APP-02。
- **通过后允许**：开展该范围的正式交互/技术设计；不授予实现完成或发布许可。

### G2 — 方案与风险（APP-04 后）

**判断问题**：方案能做、能测、能运行吗？致命未知是否已有答案？

- **输入/证据**：交互及异常状态、简要架构/接口/数据方案、风险清单、必要的限时原型或验证结果、测试策略、平台和渠道限制。
- **通过条件**：关键风险有验证而非口头假设；权限、隐私、数据生命周期、迁移和恢复方案明确；第三方依赖及签名/商店约束可满足；性能阈值与测量条件、兼容矩阵、业务目标和运行观察窗口已经固定；P0/P1 与不可豁免风险已排除。
- **负责 / 批准**：技术负责人准备并批准方案；质量负责人确认验证策略；相关安全/数据责任人确认风险，业务负责人批准业务目标及可接受边界。
- **失败返回**：方案未知留在 APP-04；交互冲突回 APP-03；成本或限制迫使范围变化回 APP-02 并重评 G1。
- **通过后允许**：建立工程基线并承诺满足 DoR 的任务；不以“方案批准”代替真实测试。

### G3 — 集成质量（APP-07 后）

**判断问题**：这个候选制品在承诺环境下是否达到质量标准？

- **输入/证据**：候选 commit + digest、构建与配置标识、设备/系统/环境清单、需求到测试映射、实际报告、缺陷清单和 P2 接受记录。
- **通过条件**：约定的功能、集成、回归及风险驱动安全/性能/兼容检查全部有结果；符合预先阈值；完成下节适用 APP 专项验证；无 P0/P1，无不可豁免风险；只允许有效 P2 条件通过。必需测试未执行或证据无法绑定制品时阻塞。
- **负责 / 批准**：质量负责人准备并批准质量结论；技术负责人确认技术风险与恢复验证，相关安全/数据负责人确认对应项。
- **失败返回**：实现问题回 APP-06，方案问题回 APP-04，环境和证据缺失留在 APP-07；标准歧义回 APP-02，不能现场降低要求。
- **通过后允许**：对同一候选制品做正式业务验收，不允许擅自替换包后沿用结论。

### G4 — 业务与发布（APP-08 后）

**判断问题**：业务是否接受这个版本，组织是否有能力安全交付和接管？

- **输入/证据**：有效 G3、相同候选基线、真实业务验收记录、[发布记录](<../../templates/release.md>)、渠道/签名准备、隐私及商店材料、监控与告警、值守、发布/暂停/恢复预案。
- **通过条件**：业务验收符合原标准；发布范围、渠道、窗口与授权明确；制品/签名/版本号一致；P2 接受未过期；监控及责任人就绪；恢复限制被明确告知并有可执行替代方案。商店审核与实际发布是后续独立状态，批准提交不等于批准宣称已上架。
- **负责 / 批准**：产品与发布负责人准备；业务负责人批准业务接受，发布负责人批准发布就绪，运行负责人确认接管。生产动作仍须在项目明确的授权范围内执行。
- **失败返回**：业务偏差回 APP-02 或 APP-06 并重评相关门禁；制品变化重走受影响 G3；材料、值守或恢复准备不足留在 APP-08。
- **通过后允许**：仅按批准计划交付对应制品；超出渠道、范围、窗口或更换制品须重新评审。

### G5 — 运行效果（APP-10）

**判断问题**：真实运行是否达到目标，哪些产品或流程变化值得进入下一轮？

- **输入/证据**：实际发布与分发记录、事先固定的指标和观察窗口、运行/业务数据、样本量与采样局限、用户反馈、事件及剩余缺陷。
- **通过条件**：窗口已完成，数据可信且足以判断；运行质量与业务目标达到预设标准；P2 接受仍有效或已关闭；改进项有责任人、期限与验证方法。数据不足为阻塞，目标未达为不通过，不得事后改口径伪装达标。
- **负责 / 批准**：运行负责人准备，产品/技术/质量参与；业务负责人批准效果判断与继续/调整/停止决定，技术负责人确认工程改进行动。
- **失败返回**：价值失败回 APP-01/02；质量问题按事件流程回 APP-06～09；流程改进进入[改进闭环](<../../factory/improvement-loop.md>)。
- **结论边界**：复盘可以完成并作出“不通过、继续实验”的明确决定；这不等于 G5 通过。继续实验须有新假设、授权与测量计划，保留原结论。G5 不追认未经批准的发布，也不替代紧急止损。

## 6. APP 专项验证清单

以下项目按项目声明的平台与风险执行；不适用需逐项说明理由，不能用模拟器结果冒充真机结果。

| 专项 | 最小需要回答的问题与证据 |
| --- | --- |
| 真机与兼容 | 在事先约定的设备、系统版本、屏幕和关键厂商组合上，核心路径、前后台切换、进程终止恢复和必要无障碍能力是否成立？报告列真实设备与系统；模拟器覆盖另列。 |
| 权限与隐私 | 首次请求、拒绝、永久拒绝、系统设置撤销、最小权限及降级路径如何表现？隐私告知、同意/撤回、敏感数据存储和日志脱敏符合承诺吗？仅使用脱敏或授权测试数据。 |
| 弱网与离线 | 超时、断网、切网、重试、重复提交、取消与恢复是否可控？避免重复扣费/写入、无限等待与无提示数据丢失；网络条件及结果可复现。 |
| 安装与升级 | 全新安装、从受支持旧版本升级、缓存/数据库迁移、登录态和数据保全是否验证？失败中断后如何恢复？明确最低支持版本与禁止降级边界。 |
| 签名与分发 | 最终发布包的应用标识、版本号/构建号、签名身份、权限声明与批准一致吗？证书/描述文件有效，升级签名兼容，测试渠道与正式渠道差异已验证；不记录私钥、口令或令牌。 |
| 商店要求 | 审核材料、隐私声明、SDK/权限披露、账号与分发资格满足目标商店要求吗？记录真实待审/被拒/获批/灰度/上架状态；商店通过不能代替内部 G3/G4。 |
| 性能与稳定性 | 以事先约定的设备、数据规模、网络、负载、测量方法及阈值评估启动、响应、资源、崩溃/无响应等相关指标；不使用任意统一数字，更不在失败后降低目标。 |
| 恢复与回滚 | 受控环境中证明暂停分发、关闭功能、服务端回退或前向修复的适用路径；验证客户端/服务端版本兼容、迁移恢复和备份可恢复性，不能只说“有备份”。 |

### 移动端回滚限制

商店分发通常不能立即撤回用户已安装的版本，也可能不允许安装更低版本；审核、灰度暂停与紧急修复存在延迟。发布前必须写清：

1. 哪些动作真的可执行，谁有权限，触发条件及预期时间是什么。
2. 如何暂停扩大影响，并维持旧客户端与服务端的兼容窗口。
3. 数据迁移是否可逆；不可逆迁移如何备份、验证恢复并避免新旧版本破坏数据。不能证明数据可恢复则阻断发布。
4. 功能开关、服务降级、前向修复是否真实具备且已验证；没有这些能力就不能写成现成兜底。
5. 发布后以实际安装/渠道核验启动观察；发生严重问题即时止损，不等 G5 窗口结束。

## 7. commit + digest 证据绑定

每次候选版本在项目运行记录与发布记录建立同一证据索引：

- **流程基线**：产线版本、工厂提交 SHA；若尚未入库，明确“工厂提交待生成”，不得编造 SHA。
- **产品基线**：产品源码完整 commit SHA；多仓库逐一列出，记录构建配置、依赖锁定信息与构建标识。未提交修改不能冒充该 commit 的内容。
- **制品基线**：待测试/发布的最终签名制品名称、平台/渠道、版本号/构建号、摘要算法与 digest（例如 SHA-256）；多个制品分别计算，不以文件名或短版本号代替摘要。
- **测试证据**：每份报告注明对应 commit、制品 digest、实际环境/设备、配置标识、执行时间、命令或人工步骤、结果与退出码（适用时）、原始日志/报告的受控位置。非制品级检查可绑定源码 commit，但不得替代候选制品测试。
- **批准与交付**：G3/G4 明确批准的同一组 commit + digest；APP-09 核对实际上传/交付对象，记录渠道凭据编号等非秘密回执、上线核验与运行版本映射。

签名、重打包、构建配置或代码变化都会产生新基线；即使 commit 相同，重新构建也不能假设 digest 相同。应计算摘要、评估影响并重跑必要检查，经受影响门禁确认后发布，禁止拿旧包报告批准新包。

商店重签名、拆包或派生分发时，上传制品与安装制品可能不同：保存上传包 digest、渠道构建标识及转换/签名关系，能取得派生制品时记录其 digest；把实际安装版本、签名与关键路径核验证据关联到同一来源链。不得声称上传包摘要就是用户安装包摘要；来源链无法核实则阻塞交付核验，不把缺少证据写成一致。
