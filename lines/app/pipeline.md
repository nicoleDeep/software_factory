# APP 产线流程 v0.1.0

> 状态：流程初版，不代表任何项目已立项、获批、通过测试或完成发布。先以 Markdown 纳入 Obsidian + Git 的知识与版本管理，再用真实项目改进；本文件本身不执行同步、提交或发布。

## 1. 使用方式与边界

- 适用于移动 APP 及配套后端；平台、商店、分发渠道和支持范围由项目声明。游戏产线只预留独立扩展边界，不把玩法验证、内容生产等假定为已经覆盖。
- 这是十类工作节点，不是十个必须串行的大阶段。以可验收的最小功能切片循环 APP-02～08；交互、风险验证、工程准备可以并行，依赖未满足的工作只能标为探索，不能冒充正式通过。
- 首次运行用[项目运行记录](<../../templates/project-run.md>)固定目标、范围、角色、指标与证据索引；切片使用[任务记录](<../../templates/task.md>)，门禁使用[门禁评审记录](<../../templates/gate-review.md>)，发布使用[发布记录](<../../templates/release.md>)。这些链接是模板入口，不是已填写的项目证据。
- 节点产物可以是同一份记录中的短段落、表格或可追溯链接，不要求每节点另写长文。必须能够回答“做什么、谁决定、证据在哪里、失败怎么办”。
- 五道决策门见[质量门禁](<quality-gates.md>)：APP-02 后 G1、APP-04 后 G2、APP-07 后 G3、APP-08 后 G4、APP-10 后 G5。节点完成不自动等于门禁通过。
- 范围、验收标准、架构、数据迁移或制品变更时，识别受影响的节点和门禁并重开；没有变化的证据可引用，不能把旧结论直接复制为新版本结论。

## 2. 角色、状态与共用约定

### 角色

项目启动时把以下角色映射到实际人员或明确授权的责任主体：产品/业务负责人、设计负责人、技术负责人、实现者、审查者、质量负责人、发布负责人、运行负责人；涉及隐私、安全或合规时指定对应负责人。未确认的名字写“待指定”，涉及其决策的节点阻塞。AI 可辅助起草、实现和汇总，不伪造人的批准。

小团队可以一人兼任多角色，但记录兼任关系；高风险变更应安排独立复核。无法提供独立复核时明确限制并由授权责任人决定是否追加外部复核，不能以兼任豁免严重风险。下文“负责”表示组织执行与保全证据，“批准”表示对退出决定负责，不表示该人已经批准。

### 状态与阻塞

节点使用“未开始 / 进行中 / 阻塞 / 待评审 / 已完成 / 已取消”；门禁结论使用[质量门禁](<quality-gates.md>)的统一状态。缺少输入、环境、凭据授权、批准人或可验证证据时，记录阻塞原因、影响、补齐责任人、预计处理时间与恢复条件，不用猜测填补。无法确定时间也应如实标记“待确认”。

任何节点的退出都必须满足本节点条件和适用的共享 DoD；进入实现工作的切片必须满足共享 DoR。探索性原型允许在正式 DoR 前进行，但须有问题、时限、隔离环境和产出，不得因此获得发布资格。

## 3. 十节点定义

### APP-01 机会判断立项

- **目的**：确认值得解决的问题，避免只因“能做”就开工。
- **准入条件和输入物**：问题或机会描述、目标用户、现有替代方案与线索；具备可联系的需求责任人。线索不足可先安排限时调研。
- **准出物**：一页立项记录，含用户场景、问题证据、价值假设、成功信号、成本/时间约束、范围初界、主要风险、角色映射和继续/暂缓/放弃决定。
- **可判定退出条件**：产品/业务负责人确认问题与投入边界；至少一个成功信号有测量方法；后续责任人与决策权限已落实。只有“继续”进入 APP-02；暂缓或放弃保留理由，不记成项目已获完整交付批准。
- **负责 / 批准**：产品负责人组织；业务负责人批准投入探索或立项。
- **失败返回**：证据不足返回调研；无价值或资源不可得则暂缓/取消，写明重新启动触发条件。

### APP-02 需求验收

- **目的**：把价值假设变成边界清晰、能被验收的功能切片。
- **准入条件和输入物**：APP-01 继续决定；用户场景、利益相关方、平台/渠道范围和约束。
- **准出物**：切片清单及优先级、纳入/不纳入范围、主路径和异常路径验收例子、业务规则、依赖、数据与隐私需求、验收责任人；性能、兼容性和运行观察指标的待确认项及截止节点。
- **可判定退出条件**：每个拟承诺切片有可复现的验收标准和业务负责人；范围冲突已解决；关键业务信息没有“待猜测”。完成 G1 评审；影响方案选择的性能、平台、数据约束在进入相关设计前确定，最迟在 G2 固定。
- **负责 / 批准**：产品负责人组织，质量/技术参与可测性审查；业务负责人批准范围与验收口径。
- **失败返回**：价值不明确回 APP-01；需求矛盾或不可验收留在 APP-02。新增范围先更新本节点，不直接塞入开发。

### APP-03 交互视觉

- **目的**：使核心任务流和异常反馈可理解、可实现、可验证。
- **准入条件和输入物**：相关切片的 G1 结论、场景与验收标准、平台规范、品牌/无障碍约束；尚未通过 G1 的方案只能作为探索。
- **准出物**：足够实现的流程/原型/界面规则；加载、空态、失败、离线、权限拒绝、登录失效、取消等状态；关键文案、可访问性要求和设计争议记录。
- **可判定退出条件**：核心与关键异常路径均有明确反馈；产品、设计、技术对可用性和实现边界形成记录；关键争议解决。可用草图，不以视觉精修替代交互完整性。
- **负责 / 批准**：设计负责人组织；产品负责人批准体验与业务表达，技术负责人确认实现可行性。
- **失败返回**：范围/规则冲突回 APP-02；方案可用性不足留在 APP-03；技术限制交 APP-04 验证后同步设计。

### APP-04 技术风险

- **目的**：先消除会推翻交付路径的未知，再承诺实现。
- **准入条件和输入物**：G1 通过的范围；相关交互方案或已标明的待决问题；平台、渠道、预算、隐私及安全约束。
- **准出物**：简要架构与接口/数据约定、技术选择理由、风险清单及限时验证证据；测试策略；性能阈值与测量条件、兼容设备矩阵、观察窗口和业务目标；迁移、降级、恢复/回滚策略；商店与签名约束。
- **可判定退出条件**：最高风险假设有证据支持或已调整范围；验证失败不包装成结论；影响交付的接口、数据、权限与依赖责任明确；测量规则在测试前固定；通过 G2。严重安全或不可恢复数据风险未解决不得退出。
- **负责 / 批准**：技术负责人组织；技术负责人批准方案，质量负责人确认可验证性，相关安全/数据责任人确认对应风险。
- **失败返回**：技术不可行回 APP-02 调整范围，价值因此失效回 APP-01；交互受限回 APP-03；缺少验证留在 APP-04。

### APP-05 工程基线拆任务

- **目的**：建立可复现、可审查、可追踪的小步交付基础。
- **准入条件和输入物**：相关切片的 G1/G2 有效结论、交互契约、测试策略和已分配责任人。
- **准出物**：可复现的工程初始化/构建说明、依赖与配置说明、环境及权限边界、检查入口、任务拆分、验收映射、分支/审查约定、证据命名和制品标识规则。凭据仅引用受控位置，不写真实密钥。
- **可判定退出条件**：按记录可准备开发及测试环境；基线构建和必要检查有实际记录，失败已处理；每项开发任务符合 DoR、大小可审查、责任和依赖明确；没有把未知事项偷偷写成已完成任务。
- **负责 / 批准**：技术负责人/实现者组织；技术负责人批准工程基线，质量负责人确认验证入口可用。
- **失败返回**：环境缺失则阻塞本节点；架构/依赖问题回 APP-04；任务验收不清回 APP-02。

### APP-06 增量开发审查

- **目的**：按功能切片实现可验证增量，同时控制变更风险。
- **准入条件和输入物**：APP-05 可用基线、满足 DoR 的任务、有效设计与接口契约、审查者。
- **准出物**：实现变更、相关单元/组件/接口测试、审查记录、缺陷处置、更新的配置/接口说明；关联任务与 commit 的变更证据。
- **可判定退出条件**：任务验收逐项自检且有证据；审查意见关闭或按规则处置；适用检查通过；无 P0/P1、无不可豁免风险；P2 仅按门禁规则限时接受。合并不等于 G3 或发布通过。
- **负责 / 批准**：实现者组织；审查者批准变更合入，技术负责人处理技术争议。
- **失败返回**：实现缺陷留在 APP-06；发现需求/设计/架构缺口分别回 APP-02/03/04；失效的门禁需重评。下一切片可再次进入 APP-05～06。

### APP-07 集成质量

- **目的**：验证组合后的候选制品，而不只验证孤立代码。
- **准入条件和输入物**：已审查增量、可识别候选制品、固定的测试范围与阈值、可用测试环境和数据、风险清单。
- **准出物**：绑定 commit + 制品 digest 的测试报告、验收项映射、缺陷清单、兼容/性能/安全与隐私检查证据；适用的真机、权限、弱网、安装升级、签名验证及恢复验证结果。
- **可判定退出条件**：约定范围已执行，未执行项不伪装为通过；环境、设备、配置与结果可追溯；阻断缺陷清零，P2 接受有效；通过 G3。制品变化须重新判断受影响检查并补证。
- **负责 / 批准**：质量负责人组织，实现者协助定位；质量负责人批准质量结论，技术/安全负责人确认对应风险处置。
- **失败返回**：缺陷回 APP-06；设计/方案缺陷回 APP-03/04；验收口径歧义回 APP-02；环境缺失则阻塞而不是判通过。

### APP-08 业务验收

- **目的**：确认候选版本解决约定业务问题，并形成可执行的发布决定。
- **准入条件和输入物**：有效 G3、同一候选制品及 digest、业务验收清单、发布与运行准备草案、剩余风险。
- **准出物**：逐项业务验收结果、真实批准/拒绝记录；发布范围、渠道、窗口、灰度/暂停条件、值守与支持安排、用户说明、合规/商店材料和恢复方案。
- **可判定退出条件**：约定业务主路径和关键异常场景得到验收；无未经同意的范围替换；业务与发布责任人均确认就绪；通过 G4。业务接受不能替代 G3 质量结论，商店待审不等于已上架。
- **负责 / 批准**：产品负责人组织业务验收，发布负责人组织上线准备；业务负责人批准业务接受，发布负责人批准发布就绪。
- **失败返回**：实现问题回 APP-06 并重走相关 G3；范围争议回 APP-02；发布准备缺失留在 APP-08；候选制品改变重评 G3/G4。

### APP-09 发布交付

- **目的**：把已批准制品受控交付到指定渠道，并能处理失败。
- **准入条件和输入物**：仍有效的 G3/G4、批准的 commit + digest、发布授权与渠道权限、签名配置引用、监控/告警与值守安排。
- **准出物**：发布记录、实际制品及渠道版本映射、签名身份/证书指纹等非秘密元数据、商店审核与分发状态、上线核验和用户交付说明；暂停、降级、前向修复或回滚执行记录（如发生）。
- **可判定退出条件**：实际发布对象与批准基线一致；目标渠道状态可核实且实际交付完成；上线关键路径及监控完成核验；运行责任人接手并开始约定观察窗口。仅已提交商店审核时维持待交付状态，不宣称发布成功。
- **负责 / 批准**：发布负责人组织；授权发布负责人确认交付，运行负责人确认接管；超出原授权的范围或窗口重新批准。
- **失败返回**：先按预案止损并记录事件；制品/代码问题回 APP-06/07，业务或渠道材料问题回 APP-08，恢复策略失效回 APP-04。移动端不能默认撤回已安装版本，按[质量门禁](<quality-gates.md>)的渠道限制处理。

### APP-10 运行复盘

- **目的**：检查实际效果，形成下一轮产品和产线改进。
- **准入条件和输入物**：APP-09 交付记录、事先约定的观察窗口与成功指标、监控/业务数据、用户反馈、缺陷与事件记录。
- **准出物**：目标与实际对照、数据口径及局限、事件复盘、剩余风险与到期 P2 检查；继续/调整/停止决定；带责任人、期限、验证方式的改进项。
- **可判定退出条件**：观察窗口结束且数据足以支持结论；不足则标记阻塞并补采，不写“默认成功”；完成 G5 决策，行动有归属。G5 可以判定效果未达标，不能为追求“通过”事后缩短窗口或降低目标。
- **负责 / 批准**：运行负责人组织，产品/技术/质量共同分析；业务负责人批准效果结论，技术负责人确认工程改进责任。
- **失败返回**：运行故障走事件处置并回 APP-06～09；价值假设失败回 APP-01/02；流程问题进入[改进闭环](<../../factory/improvement-loop.md>)。改进后以新证据重新评估，保留原失败结论。

## 4. 最小落地路径

1. 为真实项目建立一份运行记录，补齐角色和范围，不先制造十套空文档。
2. 选择一个端到端小切片，完成 G1/G2；按 APP-05～08 反复交付可验收增量。
3. 每次发布明确候选制品基线，完成 G3/G4 后由 APP-09 交付；按 APP-10 完成 G5。
4. 用真实耗时、返工、漏检与运行效果提出改进；经评审后更新产线版本，保留变更理由和旧版本引用。
5. Obsidian 用于导航与知识复用，Git 用于审阅与版本追踪；项目敏感信息、凭据和用户原始数据不直接写入可共享流程库。未经实际操作与核实，不把“计划入库”写成“已经提交”。

后续游戏产线可复用角色、证据和门禁骨架，但需另行验证玩法乐趣、内容质量、设备性能与发行运营等专门流程；本 v0.1.0 不提前定义其完成标准。
